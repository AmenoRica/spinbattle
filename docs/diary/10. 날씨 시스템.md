# 10. 날씨 시스템

## 목표

배틀에 실시간 날씨를 반영하는 시스템을 추가한다. 랜덤한 세계 도시를 선택하고, Open-Meteo API로 날씨를 가져와 전투에 영향을 준다.

---

## 무엇을 만들었나

### 날씨 API 모듈 (`weather/`)

`battle/`은 순수 Python이어야 한다는 원칙을 지키면서, 외부 API 호출은 별도 패키지로 분리했다.

```
weather/
├── __init__.py
├── cities.py    # 20개 세계 도시 (이름, 위도, 경도)
└── api.py      # Open-Meteo API 호출, 1시간 캐싱, 실패 시 "normal" 폴백
```

- **도시 목록**: 서울, 도쿄, 뉴욕, 런던, 파리 등 20개 도시. `random_city(rng)`로 배틀 시 랜덤 선택.
- **날씨 API**: Open-Meteo는 API 키가 필요 없어서 선택. WMO 날씨 코드를 4가지 카테고리로 매핑:
  - 쾌청(0, 1) / 비(51-67, 80-82, 95-99) / 눈(71-77, 85-86) / 일반(나머지)
- **캐싱**: 도시별로 1시간 캐시. API 실패 시 `"normal"`로 폴백.

### 날씨 효과 정의 (`battle/weather.py`)

`battle/` 패키지 안에는 API 호출 없이 날씨 효과만 정의한다.

| 날씨 | 효과 |
|---|---|
| **쾌청** | 불꽃 타입 공격력 ×1.15, 전기 타입 행운 ×1.10, 치명타 확률 +3% |
| **비** | 물 타입 가속 시 속도 회복 +5, 불꽃 타입 공격력 ×0.85, "빗물 유입" 턴 이벤트 |
| **눈** | 얼음 타입 방어력 ×1.20, 불꽃 타입 감속 ×1.5, "눈보라" 턴 이벤트 |
| **일반** | 없음 |

### 엔진 수정 (`battle/engine.py`)

`simulate()` 시그니처에 `weather=None`, `city_name=None` 파라미터를 추가했다. 주요 변경:

1. **배틀 시작 시 날씨 발표**: `"⚔️ 서울의 날씨: 비!"` 같은 로그와 `weather_announce` 이펙트
2. **스탯 보정 적용**: 날씨에 따른 공격력/방어력/행운 배율, 가속 보너스, 감속 배율
3. **치명타 보너스**: 쾌청 시 치명타 확률 +3%
4. **날씨 이벤트**: 비→빗물 유입(속도 회복), 눈→눈보라(속도 대폭 감소), 매 턴 일정 확률로 발생

### 프론트엔드 변경

- **배틀 헤더**: 도시명과 날씨 아이콘/이름을 표시하는 배지 추가 (쾌청=금색, 비=파랑, 눈=흰색, 일반=회색)
- **카운트다운**: 3-2-1-시작! 앞에 도시명 → 날씨 아이콘+이름 단계 추가
- **배경 이펙트**: 비=빗방울 CSS 애니메이션, 눈=눈송이 애니메이션, 쾌청=햇빛 레이 애니메이션
- **전투 로그**: 날씨 효과/이벤트에 `weather_announce`, `weather_effect`, `weather_event` 이펙트 타입 추가

## 어떤 문제를 겪었나

### 1. `simulate()` 시그니처 변경의 하위 호환성

**문제**: `simulate()`에 새 파라미터를 추가하면 기존 호출부가 모두 깨질 수 있다.

**해결**: `weather=None`, `city_name=None`으로 기본값을 설정하여 기존 호출부는 수정 없이도 동작하도록 했다.

### 2. 날씨 이벤트 인라인 처리

**문제**: 기존 랜덤 이벤트는 `_apply_event()`라는 공통 함수로 처리되지만, 날씨 이벤트(빗물 유입, 눈보라)는 조사(josa) 처리와 메시지 포맷이 달라서 별도 인라인 로직으로 작성해야 했다.

**해결**: 날씨 이벤트의 메시지는 `WEATHER_EVENT_TEXT`(다국어)에서 가져오고, 조사 처리는 `_apply_event()`와 동일한 방식으로 인라인 처리했다.

### 3. `BattleReplay.init()`에 log만 넘기던 문제

**문제**: 기존 `battle.js`에서 `BattleReplay.init(data.log)`처럼 log 배열만 넘기고 있었다. 날씨 정보(`weather`, `city`, `weather_name`, `weather_icon`)는 최상위 데이터에 있어서 카운트다운에서 도시/날씨를 표시할 수 없었다.

**해결**: `BattleReplay.init(data)`로 전체 데이터를 넘기고, 내부에서 `logData = data.log || data`로 처리하도록 변경했다. 날씨 변수(`battleWeather`, `battleCity` 등)도 `init()`에서 저장하여 `showCountdown()`에서 사용한다.

### 4. `weather_event_ids` 변수 스코프 문제

**문제**: `weather_event_ids`를 날씨 효과 적용 블록 내부에서 조건부로 정의했는데, 턴 루프 안에서 참조할 때 날씨가 `None`이면 `NameError`가 발생했다.

**해결**: `weather_event_ids = WEATHER_EVENTS.get(weather or "normal", [])`를 함수 초기 영역으로 이동시켜 항상 정의되도록 했다.

## 배운 점

- **API 호출과 비즈니스 로직의 분리**: `weather/`와 `battle/weather.py`를 분리한 것이 좋은 결정이었다. `battle/`은 여전히 Django 비의존적이고, API 호출은 별도 패키지에 있어 테스트와 재사용이 쉽다.
- **캐싱과 폴백**: 실시간 API는 실패할 수 있다. 캐싱(1시간)과 폴백(일반 날씨)을 처음부터 설계하니, API 장애 시에도 배틀이 정상 동작한다.
- **프론트엔드와 백엔드의 계약**: 날씨 이펙트(`weather_announce`, `weather_effect`, `weather_event`)를 명확한 타입으로 정의하고, JS에서 이 타입별로 분기 처리하는 패턴이 기존 배틀 이벤트와 일관성 있게 유지되었다.
